# Repository Guidelines

## Project Structure & Module Organization
VitePress reads localized Markdown and route definitions from `pages/{en,zh,ja}` and copies static assets from `pages/public`. Put page implementations in `src/features`, reusable Vue components in `src/components`, and datasets and content loaders in `src/data`. The feedback forum owns its UI, composables, API providers, services, and state in `src/forum`. Shared composables, services, and utilities live in their matching `src` folders. The import rules in `eslint.config.ts` keep forum services and API code independent of UI layers and limit imports from `src` into `.vitepress` to approved entry points. Every feature directory under `.vitepress/theme/components` and `.vitepress/theme/markdown-ext` is an import boundary, so a cross-directory import goes through that directory's `index.ts`; `local/prefer-barrel-import` enforces and rewrites this repo-wide, and leaves same-directory imports alone so barrels cannot cycle back through their own `index.ts`. Every internal specifier names the file it resolves to — `./foo.ts`, `./foo/index.ts`, `./Foo.vue` — with no extensionless or bare-directory shorthand, because VitePress loads the site config through native Node ESM; the `local/native-import-path` rule enforces and rewrites the spelling, and `tests/shared/nativeConfig.test.ts` proves the config graph still loads under plain Node. Path aliases are declared only in `.vitepress/config/aliases.ts`; `tsconfig.json` mirrors that table, and the alias test fails when the two drift. The ui components Markdown may use as MDC tags are re-exported from `.vitepress/theme/components/ui/mdc.ts`; the metadata plugin reads that file as text, so its `.vue` re-exports never join the Node graph, and adding a tag means adding an export there rather than to the barrel. Site chrome, themes, and VitePress configuration live under `.vitepress`. Utility scripts live in `scripts`, and builds write to `dist`.

## Build, Test, and Development Commands
Run `corepack enable && pnpm install` before first use. `pnpm dev` launches VitePress locally. `pnpm build` (alias `pnpm build-vitepress`) produces the static docs served at `/docs/`. `pnpm build:fonts` validates or regenerates cached font subsets before each production build: site characters only affect the `cjk.min` layer in `fonts-subset.gen.css`, while script tiers (`latin`, `latin-ext`, `symbols`, `kana`, `cjk-punct`) and pinned Google Fonts buckets keep the L1/L2/L3 WOFF2 files and `fonts-standard.gen.css` stable. Generated chunks are named `{stem}.{group}.{NN}.{hash}.gen.woff2` (e.g. `hywenhei_45w.cjk.l1.01.<hash>.gen.woff2`, `hywenhei_45w.latin.01.<hash>.gen.woff2`); all generated artifacts — the `*.gen.woff2` chunks and both stylesheets (`fonts-subset.gen.css`, `fonts-standard.gen.css`) — are gitignored and rebuilt deterministically from the committed source TTFs. The font-subset Vite plugin runs the pipeline automatically at dev/build start, so a fresh clone needs no manual step, only the Python toolchain. Font pipeline settings live in `scripts/fonts/font-subset.config.json` (including the `scripts` section with latin/latin-ext ranges mirroring VitePress `fontSubsets.json`); standard characters and Google slicing buckets live in the referenced `font-characters.config.json` and `font-slicing.config.json`. The build requires Python 3 with fonttools + brotli (`pip install -r requirements.txt`) and stops when this toolchain is unavailable. Use `pnpm build-data` when updating member or blog data; the command chains `use-data-env`, `build-member`, `pnpm lint`, `pnpm typecheck`, and `pnpm lint:md` keep TS, Vue, and Markdown quality in check. For Chinese copy edits run `pnpm lint:zh` (and `pnpm lint:zh-fix` to auto-fix common issues).

## Coding Style & Naming Conventions
The repo enforces 2-space indentation and LF endings via `.editorconfig`. Follow ESLint rules defined in `eslint.config.ts`, UnoCSS utilities, and the existing component catalogue. Vue single-file components stay PascalCase (e.g., `TeamCard.vue`), composables use `useX`, stores follow `useXStore`, and locale-specific markdown keeps kebab-case filenames. Prior to committing, rely on `pnpm lint:eslint-fix` and `pnpm lint:md` to resolve style drift.

## Testing Guidelines
All maintained tests live under root `tests/`: forum business regressions in `tests/forum/`, shared services in `tests/shared/`, theme behavior in `tests/theme/`, font build contracts in `tests/fonts/`, and Playwright page journeys in `tests/e2e/`. Keep fixtures and helpers beside their owning suite in `fixtures/` and `support/`; do not add test files to production source directories. `pnpm test` recursively discovers all Vitest `*.test.ts` files; `pnpm test:list` lists them. Use `pnpm test:forum`, `pnpm test:shared`, `pnpm test:theme` (shared + theme), and `pnpm test:fonts` for focused runs. `pnpm test:forum:ui` runs Playwright journeys; `pnpm test:theme:ui` runs the swipe-actions browser harness with its own fixtures. Browser checks stay separate from the default logic test entry. See `tests/README.md` for placement and maintenance rules. Additional quality checks include linting, type checks, localized markdown validation, and ensuring `pnpm build` completes without warnings. When touching generated content, rerun the relevant `pnpm build-*` script and spot-check the rendered page via `pnpm dev`. Document manual verification steps in your PR description.

## Commit & Pull Request Guidelines
Commits follow Conventional Commits with commitlint scopes limited to `i18n`, `forum`, `blog`, and `theme`. Use `pnpm commit` (Commitizen) for guided prompts. Keep messages imperative (`feat(theme): add dark header token`). For PRs, include a concise summary, link the tracking issue or task, attach before/after screenshots for UI shifts, and list any data scripts invoked so reviewers can reproduce.

## Data & Localization Tips
Keep data refresh credentials in `.env.data`. UI messages and localized site settings live in `.vitepress/locales`. For translation or i18n integration tasks, read the [Agent i18n workflow](.agents/i18n.md) first. The [translation guide](.github/translation-guide.md) covers contributor instructions and shared translation rules.
