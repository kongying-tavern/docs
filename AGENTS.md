# Repository Guidelines

## Project Structure & Module Organization
VitePress reads localized Markdown and route definitions from `pages/{en,zh,ja}` and copies static assets from `pages/public`. Put page implementations in `src/features`, reusable Vue components in `src/components`, datasets in `data/static` (grouped by locale), and content loaders in `data/loader`. The feedback forum owns its UI, composables, API providers, services, and state in `src/forum`. Shared composables, services, and utilities live in their matching `src` folders. The import rules in `eslint.config.ts` keep forum services and API code independent of UI layers and limit imports from `src` into `.vitepress` to approved entry points. Every feature directory under `.vitepress/theme/components` and `.vitepress/theme/markdown-ext` is an import boundary, so a cross-directory import goes through that directory's `index.ts`; `local/prefer-barrel-import` enforces and rewrites this repo-wide, and leaves same-directory imports alone so barrels cannot cycle back through their own `index.ts`. Every internal specifier names the file it resolves to — `./foo.ts`, `./foo/index.ts`, `./Foo.vue` — with no extensionless or bare-directory shorthand, because VitePress loads the site config through native Node ESM; the `local/native-import-path` rule enforces and rewrites the spelling, and `tests/runtime/shared/contracts/nativeConfig.test.ts` proves the config graph still loads under plain Node. Scripts that `package.json` runs as `node *.ts` sit under the same native-Node constraint: node only strips types, so those entry points and everything they import must stay erasable — no `enum`, `namespace`, parameter properties, decorators or `import =`, and no tsconfig aliases beyond relative paths, bare packages and `#` imports. The same guard rejects imports of `.json` files without `with { type: 'json' }` and the CommonJS globals (`require`, `module`, `exports`, `__dirname`, `__filename`): `tsc` accepts both through `@types/node`, while `node` fails at load time. Node 22.18+ on the 22 line, or 23.6 and newer, is required: those are the first releases on their line where type stripping runs without a flag. Inside `.vitepress/theme` every specifier stays relative for the same reason: the `.vitepress/config.ts` → `.vitepress/config/markdown.ts` → `.vitepress/theme/markdown-ext` chain is evaluated by native Node, which does not resolve `@theme`, so one relative-path convention keeps any theme file safe wherever it lands in that graph; code outside `.vitepress` imports theme modules through `@theme/...` instead. Path aliases are declared only in `.vitepress/config/aliases.ts`; `tsconfig.json` mirrors that table, and the alias test fails when the two drift. The `#data` prefix resolves to the `data` directory. For every Markdown file under `pages/`, a `<style src>` value stays relative to that file (for example `../../src/features/links/Join.css`) so the link checker resolves the same file VitePress loads; do not use Vite aliases or site-root paths there. The ui components Markdown may use as MDC tags are re-exported from `.vitepress/theme/components/ui/mdc.ts`; the metadata plugin reads that file as text, so its `.vue` re-exports never join the Node graph, and adding a tag means adding an export there rather than to the barrel. Site chrome, themes, and VitePress configuration live under `.vitepress`. Utility scripts live in `scripts`, and builds write to `dist`.

Every extension under `markdown-ext` must register its lowercase name in `RESERVED_BLOCK_CONTAINERS` (`comark/comarkPatches.ts`), regardless of the syntax it provides — `::: name` block, inline rule, or pure MDC component such as `Card` and `QA`:

- Comark is registered in `preConfig` and its block rule matches any `::: name`, so without an entry the name would be captured as an MDC component and dropped by the Vue compiler. `demo` depends entirely on this list; registration order does not cover it.
- The lookup runs only in the block rules and is case-sensitive against the captured source text, so a lowercase entry blocks lowercase `:::name` / `::name` blocks while leaving the PascalCase block tag (`::Card`, `::Spoiler`, `::QA`) free to render. Write an extension's block form with its capitalized tag; the inline form `:name[...]` never consults the list.
- Keep the entry for the whole life of the extension; do not remove it when the extension changes the Markdown syntax it provides.
- MDC component names are case-sensitive; write every tag in the casing its component documents (`::Card`, `:Spoiler[...]`).

## Build, Test, and Development Commands
Run `corepack enable && pnpm install` before first use. `pnpm dev` launches VitePress locally. `pnpm build` (alias `pnpm build-vitepress`) produces the static docs served at `/docs/`. `pnpm build:fonts` validates or regenerates cached font subsets before each production build: site characters only affect the `cjk.min` layer in `fonts-subset.gen.css`, while script tiers (`latin`, `latin-ext`, `symbols`, `kana`, `cjk-punct`) and pinned Google Fonts buckets keep the L1/L2/L3 WOFF2 files and `fonts-standard.gen.css` stable. Generated chunks are named `{stem}.{group}.{NN}.{hash}.gen.woff2` (e.g. `hywenhei_45w.cjk.l1.01.<hash>.gen.woff2`, `hywenhei_45w.latin.01.<hash>.gen.woff2`); all generated artifacts — the `*.gen.woff2` chunks and both stylesheets (`fonts-subset.gen.css`, `fonts-standard.gen.css`) — are gitignored and rebuilt deterministically from the committed source TTFs. The font-subset Vite plugin runs the pipeline automatically at dev/build start, so a fresh clone needs no manual step, only the Python toolchain. Font pipeline settings live in `scripts/fonts/font-subset.config.json` (including the `scripts` section with latin/latin-ext ranges mirroring VitePress `fontSubsets.json`); standard characters and Google slicing buckets live in the referenced `font-characters.config.json` and `font-slicing.config.json`. The build requires Python 3 with fonttools + brotli (`pip install -r requirements.txt`) and stops when this toolchain is unavailable. Use `pnpm build-data` when updating member or blog data; the command chains `use-data-env`, `build-member`, `pnpm lint` and `pnpm typecheck`. `pnpm typecheck` chains `typecheck:ts`, `typecheck:node` and `typecheck:vue`; `typecheck:node` is what enforces the `node *.ts` constraints above. `pnpm lint` runs ESLint and Chinese typography (`pnpm lint:zh`); Markdown structure is a separate `pnpm lint:md`, run by its own CI step and by autofix.ci. `scripts/lintMd.ts` hands mdclint the file list derived from `.markdownlintignore` (mdclint cannot read ignore files itself, so that file stays the single ignore source). Never add `"default": true` to `.markdownlint.json`: mdclint treats that key as a config file of its own and silently drops every rule override.

## Coding Style & Naming Conventions
The repo enforces 2-space indentation and LF endings via `.editorconfig`. Follow ESLint rules defined in `eslint.config.ts`, UnoCSS utilities, and the existing component catalogue. Vue single-file components stay PascalCase (e.g., `TeamCard.vue`), composables use `useX`, stores follow `useXStore`, and locale-specific markdown keeps kebab-case filenames. Component-local constants live beside the SFC that reads them: pure class/style tokens go in `styles.ts`, fixed literal tables in `constants.ts` (storage keys, selectors, timings), and the configuration a component reads — prop defaults, size maps — in `config.ts`. Prior to committing, rely on `pnpm lint:eslint:fix` and `pnpm lint:md:fix` to resolve style drift.

### Markdown Reference Definitions

Markdown reference definitions (`[text][label]` for links, `![alt][label]` for images) keep destinations in one place, so an address change does not have to be repeated and missed across a document. This is a recommended workflow, not a requirement.

When following it:

- Use `link:xxx` labels for links and `img:xxx` for images.
- Put extracted definitions at the end of the relevant section; choose small-section or large-section granularity by practical need.
- Extract same-page anchor links as well. Give every heading a semantic `{#xxx}` anchor so any heading can be targeted.
- Leave Placeholder components and links whose destination is still pending out of the definition blocks.

If an author explicitly asks to normalize a document to this workflow, confirm the concrete choices before editing: which of the optional points above apply, which range of link and image destinations to extract, and where the definitions should be placed.

## Testing Guidelines
All maintained tests live under root `tests/`, grouped by how they run: Vitest logic tests in `tests/runtime/` (`forum/`, `theme/`, `shared/`, `fonts/` domains), Playwright page journeys in `tests/e2e/` (`forum/` and `site/` domains), and component browser harnesses in `tests/harness/`; split every domain into feature modules. Shared helpers live in `tests/support/` and reusable raw-data fixtures in `tests/fixtures/`; runner-specific scaffolding stays inside its owning suite in `fixtures/` and `support/`; do not add test files to production source directories. Test imports use relative specifiers only, never path aliases, and any barrel they reach must stay free of side effects: the telemetry barrel must not re-export UI components. `pnpm test` recursively discovers `tests/runtime/**/*.test.ts`; `pnpm test:list` lists them. Use `pnpm test:runtime`, `pnpm test:forum`, `pnpm test:shared`, `pnpm test:theme` (shared + theme), and `pnpm test:fonts` for focused runs. `pnpm test:forum:ui` runs the Playwright journeys for the `forum/` and `site/` domains; `pnpm test:theme:ui` runs the keyboard-shortcut and swipe-actions browser harnesses with their own fixtures. Browser checks stay separate from the default logic test entry. See `tests/README.md` for placement and maintenance rules. Additional quality checks include linting, type checks, localized markdown validation, and ensuring `pnpm build` completes without warnings. When touching generated content, rerun the relevant `pnpm build-*` script and spot-check the rendered page via `pnpm dev`. Document manual verification steps in your PR description.

## Commit & Pull Request Guidelines
Commits follow Conventional Commits with commitlint scopes limited to `i18n`, `forum`, `blog`, and `theme`. Use `pnpm commit` (Commitizen) for guided prompts. Keep messages imperative (`feat(theme): add dark header token`). For PRs, include a concise summary, link the tracking issue or task, attach before/after screenshots for UI shifts, and list any data scripts invoked so reviewers can reproduce.

## Data & Localization Tips
Keep data refresh credentials in `.env.data`. UI messages and localized site settings live in `.vitepress/locales`. For translation or i18n integration tasks, read the [Agent i18n workflow](.agents/i18n.md) first. The [translation guide](.github/translation-guide.md) covers contributor instructions and shared translation rules.
